# X27 gauges: remove the stepper axis extension, add VID6606 and direct-GPIO drive

Status: reviewed (Fable, 2026-11-08), revised. Target firmware 3.3.0.

## Decisions already made (by the user)

1. **Remove the whole stepper axis extension** added in 3.1.0: message types 16/17,
   the `Stepper::Controller`, the PCA9685/TB6612 driver, shield registration and all
   I2C safety gating. The numbers stay reserved and are never reused.
2. **Gauges are a normal module type**, configured with `Configure`, stored in EEPROM
   like buttons and displays, and driven with a new message.
3. **Zeroing**: automatic when the gauge starts (boot or new configuration), plus a
   host command to re-zero later.
4. **Step timing from a hardware timer interrupt**, not from `loop()`.

### Compatibility

- A 3.1/3.2 host that sends type 16 gets no reply, like any unknown message. The
  changelog says hosts must not assume the axis extension from the version number.
  Nothing is known to use it (same reasoning as the 3.2.1 removal).
- `EEPROM_FORMAT_VERSION` stays 5. Stored module records are unchanged; axis config
  was never stored. A 3.2 firmware reading a 3.3 record with type 7 fails the load and
  boots unconfigured (existing behaviour for unknown types).

## Part B: X27 gauge module

### Hardware

| Driver | Wiring | Resolution | Limits |
| --- | --- | --- | --- |
| VID6606 (and clones: AX1201728SG, BY8920) | STEP + DIR per motor, 4 motors per chip | 1/12 degree per STEP rising edge; 315 degrees = 3780 pulses | STEP high and low each >= 450 ns; DIR setup 100 ns; motor limit 7.2 kHz (600 deg/s). VDD 4.5-5.5 V, inputs VIH 3.15 V (3.3 V logic works but is marginal). RESET active-low, held low >= 1 ms after power-up by the board's RC network; firmware does not drive it. |
| Direct GPIO | 4 MCU pins to X27 contacts 1..4 | 1/3 degree per step, six-state Switec pattern; 315 degrees = 945 steps | Coils 230-290 ohm, about 20 mA each at 5 V, two coils on in four of six states. **AVR only** for driving coils straight from pins; add flyback diodes. Document 1-2 direct gauges per board (4 gauges is about 160 mA, near the AVR 200 mA VCC limit). |

X27 (Switec table, confirm against the Juken PDF during hardware testing): 600 deg/s with
a ramp, **200 deg/s start-stop**, practical acceleration about 4000-5000 deg/s^2.

### Protocol

**`MODULE_TYPE_GAUGE = 7`** (3 is reserved for BLDC, 5 and 6 for the removed I2C input
chips). `Configure` payload, 12 bytes, **exact length required** (stricter than the
older decoders' `length <` checks; state this in PROTOCOL.md):

| Offset | Type | Field | Accepted |
| --- | --- | --- | --- |
| 0 | u8 | driver | 0 = VID6606 step/dir, 1 = direct GPIO six-state |
| 1..4 | u8[4] | pins | VID6606: STEP, DIR, 0xff, 0xff. Direct: X27 contacts 1, 2, 3, 4. All used pins distinct. |
| 5 | u16 LE | travel | steps from the stop to full scale, 1..4000 (VID6606 typical 3780, direct 945) |
| 7 | u16 LE | max_speed | steps/s, 1..5000 VID6606, 1..1800 direct |
| 9 | u16 LE | acceleration | steps/s^2, 1..60000 (document sane defaults: about 50000 VID6606, 1500 direct) |
| 11 | u8 | flags | bit0 reverse direction; other bits must be 0 |

The VID6606 ceiling is 5000, not 7200, because of the STEP pulse rule below (one step at
most every second tick at 10 kHz). That is about 417 deg/s, twice the start-stop rate.

`pins[0]` is the gauge's identity pin (`getPin()`), like other pin-addressed modules.

**`MESSAGE_TYPE_SET_GAUGE_POSITION = 18`** (host to device): `pin u8, position u16 LE`.
Steps from zero, **clamped** to `travel`. Latest target wins; fire-and-forget, no
reply, like `SetOutput`. Unknown pin or non-gauge module: ignored.

**`MESSAGE_TYPE_ZERO_GAUGE = 19`** (host to device): `pin u8`. Re-runs the zero sweep,
then moves to the latest target.

No status message in this version. The host owns calibration (value to steps). Hosts
gate gauge use on firmware >= 3.3.0.

### Config validation and storage

- `ConfigManager` validates each gauge part when it arrives: driver in {0, 1}, used pins
  distinct, unused VID6606 pins 0xff, ranges per driver, reserved flag bits 0.
- **`MAX_GAUGES` (4) is checked when the configuration completes**, not in `addPart`,
  because parts may arrive in any order and repeat. More gauges is a
  `ConfigurationError`.
- EEPROM save/load writes the 12 payload bytes **field by field** (u16 fields LE), like
  `storeToEEPROM` does for other types; never memcpy the union (padding differs on
  native/ESP32). Record is 13 bytes, under the matrix's 19, so the 162-byte budget and
  the union sizes do not change.
- `loadFromEEPROM` repeats the same range checks and returns false like the matrix path
  (`config_manager.cpp:271`), so a corrupt record cannot create a stalled gauge.

### Behaviour

- `begin()`: pins to OUTPUT, register with the scheduler, start zeroing. On
  `ARDUINO_SAM_DUE` and ESP32, `begin()` returns false for `driver = 1` (pin current
  limits: SAM3X 3 mA, ESP32 about 12 mA). That shows up as the usual init error,
  reported as `ModuleError(i2c_address = 0)`, an existing limitation for pin modules that
  PROTOCOL.md should mention.
- **Zeroing**: drive `travel` steps toward zero at a fixed rate with no ramp, then set
  position 0. `ZERO_SPEED` is 2400 pulses/s for VID6606 and 600 steps/s for direct (both
  200 deg/s, the X27 start-stop limit), or `max_speed` if that is lower. This works from
  any unknown start because the internal stop blocks the needle. Targets received while
  zeroing are stored and applied afterwards.
- **Every reconfiguration re-zeros every gauge** (about 1.6 s for 3780 pulses), because
  `applyConfiguration` recreates all modules. Acceptable; document it.
- Coils stay energized at rest (direct GPIO); VID6606 holds by itself.

### Motion math (per tick, integer only, inside the ISR)

- Velocity `v` is **u32 Q24 steps/tick**: 7200 steps/s at 10 kHz is 0.72 steps/tick, about
  12.1 M, which fits. `a_tick = ((uint64_t)acceleration << 24) / (TICK_HZ * TICK_HZ)` and
  `v_max` are computed once in `begin()`; no division in the ISR. (Q16 was rejected: it
  rounds accelerations under about 1500 steps/s^2 to zero.)
- 32-bit accumulator: `acc += v`; when `acc >= 1 << 24`, subtract and take one step. At
  most one step per tick.
- Ramp state machine: ACCEL (`v += a_tick`, capped at `v_max`), CRUISE, DECEL
  (`v -= a_tick`). `ramp_steps` **increases only in ACCEL, decreases only in DECEL, and is
  frozen in CRUISE**. Switch to DECEL when `remaining <= ramp_steps`.
- While `remaining > 0`, floor `v` at `a_tick` so braking cannot reach 0 before arrival.
  Stop when `remaining == 0`, whatever `v` is.
- Retarget in the same direction, still reachable: keep going (re-enter ACCEL or CRUISE).
  Retarget behind, or closer than `ramp_steps`: brake to a stop, overshooting if needed,
  then move back (AVR446 behaviour). Tests assert exactly this.
- At top speed the step interval alternates between 1 and 2 ticks (100/200 us). That is
  fine for VID6606 microsteps; mention it in ARCHITECTURE.md.

### Pin output per tick

- **VID6606 STEP**: at the **start** of each tick, clear any STEP pin raised by the
  previous tick; then raise STEP for gauges that step now. This gives a 100 us high time
  on every architecture with no busy-wait. To keep the low time >= 450 ns as well, a
  VID6606 gauge never steps on two ticks in a row; that is what the 5000 steps/s
  ceiling enforces (`v_max <= 0.5 steps/tick`).
- **VID6606 DIR**: changes only while stopped, so it is set at least one tick before
  the next STEP (setup 100 ns).
- **Direct GPIO**: phase +-1 mod 6, write four pins from the six-state table.
- **FastPin `{volatile reg*, mask}`**, built by `makeFastPin(pin)` declared in
  `gauge_timer.h` and implemented in each backend file
  (`portOutputRegister(digitalPinToPort())` on AVR, PIO `SODR/CODR` on SAM,
  `GPIO.out_w1ts/w1tc` on ESP32, a recording mock on native). No `digitalWrite` in the ISR.
- AVR rule: main-loop writes to a port shared with gauge pins must go through
  `digitalWrite` (it disables interrupts around the read-modify-write). The current
  tree complies; note it in ARCHITECTURE.md.

### Scheduler and timer

`GaugeScheduler` holds up to `MAX_GAUGES` gauge pointers and runs one timer interrupt
at `TICK_HZ = 10000` while at least one gauge is registered. It stops the timer when
the last gauge unregisters, so boards without gauges are unaffected. `TICK_HZ` and
`MAX_GAUGES` are `constexpr`. Estimated ISR cost on a 16 MHz AVR with 4 gauges: about
15 percent of each tick.

| Arch | Timer | Notes |
| --- | --- | --- |
| AVR (32U4, 328P, 2560) | Timer1, CTC, prescaler 8, `OCR1A = F_CPU/8/TICK_HZ - 1` | Confirmed free: millis is Timer0, 32U4 USB CDC, PacketSerial, Wire and EEPROM use no timer, and the tree has no `analogWrite`, tone or Servo. Write `TCCR1A = 0` explicitly (the core leaves phase-correct PWM). On stop, clear `TIMSK1` and the clock-select bits. Takes over Timer1 PWM pins (328P: 9, 10; 32U4: 9, 10, 11; 2560: 11, 12, 13) while gauges run. |
| SAM (Due) | TC1 channel 0, `TC3_Handler` | Free (analogWrite uses TC0/TC2). Enable `ID_TC3` clock, MCK/8, RC = 1050; read `TC_SR` in the handler to clear the flag. |
| ESP32 | hardware timer 0, 2.x API: `timerBegin(0, 80, true)`, alarm 100 us | The unpinned `espressif32` platform resolves to 6.12.0 / Arduino core 2.0.17. `#error` if `ESP_ARDUINO_VERSION_MAJOR != 2` rather than ship an untested 3.x branch. The ISR runs on core 1 like `loop()`, so `noInterrupts()` is enough. |
| native | none | Tests call `GaugeScheduler::tick()` directly. |

### Concurrency rules

- Targets and zero requests written from `loop()` go into the motion object under
  `noInterrupts()/interrupts()` (16-bit writes are not atomic on AVR).
  Add both functions to `test/Arduino.h`.
- **Unregister before delete**: `GaugeModule`'s destructor removes itself from the
  scheduler with interrupts off; the scheduler stops the timer when empty.
  `applyConfiguration` deletes all modules on every reconfiguration.
- The ISR touches only scheduler state and pins; it never allocates or sends serial.
- **Flash writes while the ISR runs (blocking issue from review)**: `handleConfigure`
  commits EEPROM *before* `applyConfiguration` deletes the old gauges. On ESP32 an ISR
  that reaches non-IRAM code during a flash operation panics. Do both:
  - mark everything the ISR reaches `IRAM_ATTR` (handler, `GaugeScheduler::tick`,
    `GaugeMotion::tick`, FastPin writes) and the six-state table `DRAM_ATTR`
    (empty macros on other platforms);
  - add `GaugeScheduler::suspend()/resume()` and wrap `eeprom_commit()` with it on ESP32
    and Due (`DueFlashStorage` writes flash with interrupts on). Needles pause briefly
    during a save; acceptable.

## Tests

- Motion: ramp up, cruise at `max_speed`, brake to the exact target, `ramp_steps` frozen
  in cruise, low accelerations (1, 100, 1000 steps/s^2) actually accelerate, retarget
  same direction and behind (overshoot and return), clamp to travel, zero sweep length,
  rate and final position, target received during zeroing, re-zero.
- Module: six-state sequence forward, backward and reversed; VID6606 DIR before STEP,
  STEP cleared at the next tick, never two consecutive STEP ticks; destructor
  unregisters; direct driver refused on Due/ESP32 builds (compile-time test if practical).
- Scheduler: timer starts on first register, stops on last unregister, suspend/resume.
- Protocol and config: exact-length decode, every range rejection, duplicate pins,
  five gauges rejected at completion in any part order, EEPROM round trip, corrupt
  record rejected on load, a stored type-7 configuration loads.
- Removal: types 16/17 decode as unknown; nothing reads EEPROM 500..504.
- Build all 8 board environments (`pio run`) and `pio test -e native`. Compare Uno RAM
  (baseline 1339/2048 static with the stepper code) and Pro Micro flash (baseline 75.7%).

## Hardware verification (manual)

1. Pro Micro + VID6606 + one X27: zero sweep at boot, full-scale sweeps at increasing
   `max_speed` and acceleration until steps are lost; record safe defaults.
2. Same board, direct GPIO X27: same.
3. ISR time: toggle a spare pin around the handler, scope it with four gauges moving and
   a matrix configured. Budget: under 30 percent of the 100 us tick.
4. HT16K33 and matrix scanning still behave while gauges move; a reconfiguration during
   motion re-zeros cleanly.
5. ESP32: reconfigure while a gauge moves; no panic.

## Resolved questions

1. 10 kHz tick, at most 4 gauges, both `constexpr`.
2. `SetGaugePosition` clamps.
3. VID6606 RESET is left to the board's RC network.
4. `SetOutput` on a gauge pin is ignored (cheap guard).
5. Version 3.3.0, following the 3.2.1 precedent.

## Implementation notes (deviations from the reviewed plan)

- **VID6606 RESET_N is driven by firmware after all.** The train-lever gauge board
  (rev 3) puts RESET_N on D6 with a 10 k pull-down, so the chip never leaves reset
  unless firmware raises it. `pins[2]` is now RESET_N (or 0xff). Gauges sharing it
  pulse it once (`GaugeScheduler::claimReset`).
- **JTAG is turned off at startup** on 32U4/2560: the board's gauge C uses A3/A2
  (PF4/PF5, JTAG TCK/TMS).
- **Q32 velocity with carry detection**, not Q24: Q24 still rounds accelerations
  below 6 steps/s^2 to zero.
- **Speed floor is sqrt(2a)**, the speed after one step from rest, not `a_tick`:
  an `a_tick` floor crawls at about 0.1 steps/s near the target.
- **Arrival rule**: stop when the ramp is spent (`ramp_steps <= 1`) and the needle
  is at or past the target; an early "stop at target whatever the speed" would
  defeat the overshoot behaviour for late retargets.
- **Zero sweep covers the full 315 degrees** (3780 / 945, or `travel` if larger), not
  `travel`, so a needle left beyond a short dial's travel still reaches the stop.
- **Direct drive on Due/ESP32 is refused at Configure time** (ConfigurationError),
  not in `begin()`, so it never reaches the init-error path.
- The `% 6` and the 32-bit multiply were removed from the ISR path.
- Wiring guide: [docs/GAUGE_WIRING.md](../../GAUGE_WIRING.md), diagrams generated by
  `docs/wiring/make_diagrams.py`.
